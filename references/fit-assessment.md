# 适合度与推荐度

推荐度回答“这个 Skill 对当前用户或写明的适用用户值不值得采用”，由适合度和好用度（见 [quality-score.md](quality-score.md)）合成，不再单独打分。0 表示不推荐，10 表示强推荐。共用计算规则见 [scoring-rubric.md](scoring-rubric.md)。

## 两种判断对象

- 用户选择“需要结合我的需求评估”并回答“你希望这个 Skill 能帮你做什么”：目标匹配和交付匹配都按用户实际需求打分；
- 用户选择“按一般目标用户进行评估”：根据官方定位界定一般目标用户，并在报告中写清这类用户是谁；目标匹配默认按 6 分（中等）起评，交付匹配仍按证据正常打分。

不得把适用用户写成必然满足所有条件的完美用户。

## 适合度：目标匹配 × 0.65 + 交付匹配 × 0.35

两项都独立打分（0—10，允许一位小数），按上面的权重合成适合度（0—10）。目标匹配权重更高，因为方向不对，交付再好也没用；方向对了，交付差一点还能凑合用。

**评分前提：假设候选对象已经完整安装并配置到位，不因为某个可选功能、渠道或平台尚未安装而扣分。** 安装这件事的负担已经在好用度的“安装复杂度”里体现，这里不重复扣分；理由里不得出现“没装”“未安装”“还没装”这类以安装状态为依据的表述。

### 目标匹配分档（0—10）

只判断“假设已完整安装配置，这个 Skill 的实际能力能不能覆盖需求”，不判断安装成本：

| 分数 | 判断 |
| --- | --- |
| 9—10 | 完全命中核心任务，没有明显缺口 |
| 7—8.9 | 命中核心任务，有次要缺口（工具能力边界，不是安装问题） |
| 5—6.9 | 部分命中，核心能力有限或需要绕路 |
| 3—4.9 | 只能算沾边，主要靠辅助功能凑合 |
| 0—2.9 | 基本不解决核心任务 |

一般用户模式默认 6 分起评，代表“官方说要服务的就是这类人，方向大致成立，但还没证实”；找到证据证明它确实做到自己宣传的效果，上调到 8—10；找到证据证明货不对板，下调到 3 分以下。

### 交付匹配分档（0—10）

只判断“格式、质量、可编辑性和可验证方式是否满足要求”：

| 分数 | 判断 |
| --- | --- |
| 9—10 | 交付物完整满足需求，可直接使用或核对，没有缺口 |
| 7—8.9 | 交付物基本满足，有次要缺口 |
| 5—6.9 | 交付物部分可用，还需要用户自己补充加工 |
| 3—4.9 | 交付物粗糙，大部分还要返工 |
| 0—2.9 | 交付物基本不可用 |

## 推荐度：基础分 + 适合度封顶

基础分的公式是：基础分 = 好用度 × 0.45 + 适合度 × 0.55。

再用适合度本身给基础分设一道封顶（不重新打分，只是复用适合度这个数字）：

| 适合度 | 推荐度封顶 |
| --- | ---: |
| ≥7 | 不封顶 |
| 5—6.9 | 最高 7.4（到不了“推荐”档） |
| 3—4.9 | 最高 5.9（到不了“有条件推荐”档） |
| 0—2.9 | 最高 3.9（直接锁进“不推荐”） |

推荐度 = min(基础分, 适合度对应的封顶值)，四舍五入保留一位小数。

安装复杂度不作为推荐度的封顶依据：安装成本高只说明“值不值得为它多花点功夫”，这件事已经在基础分里通过好用度体现过一次，不该再单独否决一个方向对、交付好的 Skill。

## 等级

| 分数 | 推荐结论 |
| --- | --- |
| 0—3.9 | 不推荐 |
| 4.0—5.9 | 谨慎采用 |
| 6.0—7.4 | 有条件推荐 |
| 7.5—8.9 | 推荐 |
| 9.0—10 | 强推荐 |

## 硬条件

- 核心执行路径不成立、许可证明确不允许、必需环境缺失且不可替代：直接不推荐，不看算出来的分数；
- 硬条件证据缺失：给推荐区间并标 `证据不足`；
- 有条件推荐必须在结论中列出具体条件，不能只写标签；
- 公开关注度已经计入好用度，不再算作“不直接计入推荐分的背景信息”；
- 下载量只有找到公开数值时才使用；
- 安装复杂度或任务复杂度低不等于值得装，风险低也不等于结果可靠——这两件事已经分别体现在好用度和适合度里，不需要额外强调。

## 结论写法

必须同时写：

1. 推荐程度与分数；
2. 本次判断对象或具体判断依据；
3. 适用场景；
4. 主要限制；
5. 一句明确的采用建议。

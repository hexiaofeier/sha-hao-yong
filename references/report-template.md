# 固定 HTML 报告模板

最终交付为单文件 HTML。结构、样式、推荐总分、推荐等级、评估范围、判断对象和页尾说明第二条由 `scripts/render_report.py` 唯一控制。

## 强制生成方式

1. 运行 `python scripts/render_report.py init <Skill名称> --output-dir <交付目录>`；
2. 只填写生成的 schema v13 过程 JSON；
3. 运行 `python scripts/render_report.py check <过程JSON路径>`；
4. 修正全部问题后运行 `python scripts/render_report.py build <过程JSON路径>`；
5. 脚本把 HTML 生成到 `过程文件_CO/` 的上一级目录；
6. 禁止手写 HTML、CSS，禁止渲染后人工修改正文。

确需指定 HTML 位置时：

```bash
python scripts/render_report.py build <过程JSON路径> --output <最终HTML路径>
```

旧格式不兼容，v12 及更早过程 JSON 必须重新评估后生成 schema v13。

## assessment_context

- `audience_mode`：`target` 表示一般目标用户；`personalized` 表示结合用户需求；
- `audience`：直接写目标人群或用户需求，不带固定前缀；
- `public_materials`：本次读取的官方材料清单。

不再记录安装状态或设备检查：好用度和适合度评分假设候选对象已完整安装配置，评估者本机是否已经安装，不进入 JSON、也不影响任何分数。

### 自动生成文字

渲染器根据 `assessment_context` 生成：

- 页首评估范围；
- 推荐条旁的判断对象；
- 页尾说明第二条。

这三处不进入 JSON 自由填写，避免口径互相冲突。

## benchmark_task

固定常规任务的抽取规则见 [evaluation-context.md](evaluation-context.md)。

- `version`：同一基准保持相同版本；
- `goal/input/workload/output/source`：必须完整填写；
- `changed`：首次评估和沿用旧基准时为 `false`；
- `change_reason`：只有 `changed` 为 `true` 时填写。

任务复杂度、Token 和风险值的说明必须写“固定常规任务”。安装复杂度说明必须写“从零安装”。

## preparation（安装准备）

安装准备固定四行、三列。`required` 必须是 1—3 条结构化短句，页面按“使用范围｜**必要程度**｜具体条件”显示。

- `scope`：2—8 字，同一行不得重复；
- `status`：软件、账号、Key 只允许 `必须／按条件／可选／不需要`；数据与隐私只允许 `必然涉及／按条件／不涉及`；
- `detail`：写明具体对象或触发条件，不能只写状态，也不能使用“按需／视情况／看情况”；
- 单条可见文字按 `scope + status + detail + 两个“｜”` 计算，最多 45 字；45 字通过，46 字失败；
- `impact`：只写需要采取的行动、费用、维护或风险，不重复中间列的采用条件。

四行职责固定：

1. 软件：基础运行环境与扩展工具；
2. 账号：默认功能是否要账号，以及哪些来源需要登录；
3. Key：免费基础功能与可能付费的扩展服务；
4. 隐私：必然发送的数据、条件性凭证和本地存储。

正确示例：

```json
{"scope": "扩展来源", "status": "按条件", "detail": "部分来源还要安装对应命令行工具"}
```

错误示例：

```json
{"scope": "扩展来源", "status": "按条件", "detail": "按需配置"}
```

错误原因：没有写出具体对象或触发条件。`"required": "必须"`、空列表、4 条内容、重复 `scope` 和非法 `status` 都会被渲染器拒绝。

## positioning（页首 Skill 定位）

- 第一句写目标 Skill 名称和真实身份；
- 第二句要写清三件事：基于什么能力基础（句中要有“基于”二字，可以直接点出具体服务名/模型名，不用回避）、通过什么方式（句中要有“通过”二字）、完成什么任务；
- 第三句写最终用户能得到什么；
- 第四句写更适合谁（可选）。

判断“是否把 Skill 自己重复当主语”只看句子是不是以 Skill 名称**开头**，不是看名称有没有作为子串出现在句子任何位置——第三方依赖的域名/服务名即使字面上包含 Skill 名称（比如 anysearch 依赖 api.anysearch.com），只要不是拿它给 Skill 自己做主语，就正常写，不用回避成模糊的类型词。

## recommendation

推荐总分不再手填，由渲染器按下列步骤自动算出：

1. **好用度**（0—10）：由 `recommendation.quality.dimensions` 里的 8 个维度加权合成，权重和计算方法见 [quality-score.md](quality-score.md)。风险值、安装复杂度、任务复杂度、Token 消耗四项填 `raw10`（对应文件算出的 0—10 分，脚本自动换算）；公开关注度、可验证性、额外涉及费用、Skill 调用准确性四项填 `score`（按 quality-score.md 的分档表直接给 0—2）。
2. **适合度**（0—10）：由 `recommendation.match` 里的 `goal_fit`、`deliverable_fit` 两项（各 0—10，一位小数）按 0.65:0.35 加权合成，分档表和评分前提（假设已完整安装配置）见 [fit-assessment.md](fit-assessment.md)。
3. **推荐度**（0—10）：基础分 = 好用度 × 0.45 + 适合度 × 0.55，再按适合度分档封顶，公式和封顶表见 [fit-assessment.md](fit-assessment.md)。

| 总分 | 等级 |
| --- | --- |
| 0—3.9 | 不推荐 |
| 4.0—5.9 | 谨慎采用 |
| 6.0—7.4 | 有条件推荐 |
| 7.5—8.9 | 推荐 |
| 9.0—10 | 强推荐 |

过程 JSON 不填写好用度、适合度、推荐度或等级，全部由渲染器算出。渲染器会在“这个 Skill 好用吗”摘要最前面自动加一行“好用度：X.X/10。”并标红加粗放大，`quality_summary` 只写“完整度……”这段描述本身，不用自己提“好用度”这几个字或数字；在“这个 Skill 适合你吗”顶部结论最前面自动加一行“适合度：X.X/10。”并标红加粗放大，下面接最终结论第一句和使用建议。不显示八个维度和两个匹配度的拆分明细。量化分析两句里的“好用度 X.X/10”“适合度 X.X/10”也会被渲染器自动识别并标红——这里**只变字色，不加粗、不放大字号**，跟上面两处大号展示是不同的样式，写作时按大白话正常写数字即可，不用额外加标记。

`goal_fit.reason` 里不得出现“没装”“未安装”“还没装”这类以安装状态为依据的表述。

## final_conclusion（最终结论，固定 4 句）

覆盖是否匹配需求、应用场景、能力基础、核心优势、不足这 5 个要点：

1. 带目标 Skill 名称说明是否匹配需求，后面顺带一个小短句说清适合什么场景（跟“这个 Skill 适合你吗”一节的“适合场景”卡内容可以重叠，两边都要写）；
2. 必须包含“能力基础”四个字，说清它靠什么、依赖谁完成任务；
3. 写核心优势；
4. 写不足或需要注意的地方。

详细句式模板见 [writing-style.md](writing-style.md)。

## what（这个 Skill 是啥）

- `summary`：句式和内容跟页首定位第二句一致，但要更详细——写清这是一个用来干什么的 skill、主要依赖什么能力基础（可以点出具体服务名/模型名）、通过什么方式、完成什么任务、主要服务什么样的用户。不再单独设 `capability_basis` 字段，能力基础的具体内容直接写进这一行摘要；
- `usage`（原 `user_needs` 已改名）：2—6 条，说明能用来做什么，正文不出现“用户”这个主语；
- `steps`：3—5 条任务步骤；
- `extra_needs`：2—4 条，额外依赖，正文不出现“用户”这个主语；
- `output`：2—4 条，最后交付，正文不出现“用户”这个主语。

以上四张卡每条不超过 35 个汉字；`summary` 不受 35 字限制，也允许出现“用户”。

## 指标表数字口径

风险值、安装复杂度、任务复杂度、Token 消耗这四项，指标表“评估结果”列只写等级（比如“中等”“很简单”“低”），不写 0—10 原始分；原始分只进 `recommendation.quality.dimensions` 对应的 `raw10` 字段，用于好用度计算，不在指标表里重复出现。好用度、适合度、推荐度这三个合成分数才需要显示具体数字，位置见上一节。

## 固定页面结构

### 页首

- 标题；
- 评估日期和自动生成的评估范围；
- 3—4 句 Skill 定位，第二句说明能力基础、方式和任务。

### 1. 结论概述

- 自动计算的推荐分、等级、判断对象和 10 格推荐条；
- 单框结构：最终结论（4 句，每句单独一行）、量化分析（好用度、适合度数字标红，不加粗不放大，每句单独一行）。不再单设“适用场景”块。

### 2. 这个 Skill 是啥

固定一行摘要（含能力基础的具体内容），加四张 2×2 卡片：使用方法、任务步骤、额外需要、最后交付。四张卡每条不超过 35 个汉字，正文不出现“用户”这个主语。

### 3. 这个 Skill 好用吗

- 摘要固定两行：第一行“好用度：X.X/10。”自动生成并标红加粗放大；第二行是质量摘要，依次出现“完整度”和优势/不足权重；
- 好用之处与可能卡住；
- 固定指标表（8 行，含可验证性；表头居中，前两列内容居中，第三列不变）；
- 固定安装准备表（表头居中，中间列为 1—3 条分层短句列表）。

### 4. 这个 Skill 适合你吗

顶部结论固定两行：第一行“适合度：X.X/10。”自动生成并标红加粗放大；第二行是渲染器根据分数重新生成的判断句（不是最终结论第一句原文，不带场景短句）。个性化需求模式下是“匹配判断 + 使用建议”两句拼接，末尾自动补句号，比如“【Skill 名称】匹配你的需求。建议安装。”；按目标人群判断时只有**一句话**，直接取 `assessment_context.audience` 拼进句子说清“适合谁安装”（不写“这类用户”这种空泛指代），不再单独拼使用建议，比如“【Skill 名称】更适合经常需要海选、筛选候选 Skill 的用户安装。”。下方并列显示“适合场景”和“不适合场景”两张卡。

### 5. 使用节奏建议

写第一次试用、扩展、复盘和停用动作。

### 页尾

1. 来源与尚不能确认的事项；
2. 说明：
   - 第一条解释 AI agent；
   - 第二条自动生成，说明报告是静态检查、不代表本机实际使用体验，并简要提一句推荐度由好用度和适合度加权平均得出；
   - 后续为专业评测边界、安全提醒和用户确认要求。

## 版式

固定使用“白纸墨字”：

- 页面底色 `#FFFFFF`，正文 `#17181A`，次要文字 `#676C74`；
- 细线 `#E3E5E8`，浅底 `#F5F6F7`；
- 点缀色为砖红 `#B73F42`、深蓝 `#244C66`、暖金 `#D6A553`、灰绿 `#82B29B`；
- 推荐条使用 10 个砖红单色色块；
- 页面不使用渐变、阴影或大面积彩色底；
- 正文、列表和表格为 `15px`，页尾说明为 `12px`；
- 所有信息卡/表格的小标题（最终结论、量化分析、使用方法、任务步骤、额外需要、最后交付、好用之处、可能卡住、适合场景、不适合场景、两个表格的表头）统一 `15px`；
- “这个 Skill 是啥/好用吗/适合你吗”三节标题下方的摘要框，除了标红的得分数字外，其余文字统一 `15px`。

## 校验要求

- 只接受 schema v13，明确拒绝 v12 及更早格式；
- 好用度 8 个维度和适合度 2 个维度必须完整，推荐度由脚本计算；
- 安装准备固定四项且顺序不变，中间列必须符合结构、枚举和 45 字限制；
- 指标表固定 8 行，含新增的“可验证性”；
- 下载量只有公开数值时才显示；
- 许可证未确认时不得写“核心免费”或“无新增费用”；
- 报告不得含待填写项、禁用表达或未解释缩写；
- 评估范围、判断对象和页尾第二条必须由渲染器生成；
- `fit` 必须同时包含 `good_for` 和 `not_for`（各 2—4 条）；
- `recommendation` 不再接受 `use_cases`，`what` 不再接受 `capability_basis`，字段名是 `usage` 不是 `user_needs`；
- 定位第二句和最终结论第二句判断“是否重复 Skill 名称”只看句首，不看子串——第三方服务名/域名即使包含 Skill 名称也可以正常写。

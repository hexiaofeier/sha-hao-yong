# 专业报告说人话规则

本文件只约束用户最终看到的文字。判断依据与评分过程仍按各自 Reference 执行。

## 总原则

- 结论前置。先回答匹不匹配、能不能用、好不好用、值不值得装。
- 正面表达。知道什么就直接说什么，不预设用户误解。
- 一句只讲一件事。长内容拆成平行短句或列表。
- 同一事实只出现一次。身份、数据、场景和建议各放在自己的位置。
- 默认读者是行政、内容、业务这类非工程背景的办公人员，不是程序员或工程师。命令名、函数名、协议名（比如 `get_sub_domains`、JSON-RPC、批量并行检索）能不写就不写，只有不得不用时才以最小程度加入，而且要让专业名词服务于人话，不能让人话给专业名词让路。
  反面：`get_sub_domains 加 1 次垂直搜索，返回最多 5 条 JSON 结果，Agent 读取解析即可。`
  正面：`先自动判断问题属于哪个类别，再搜一次，最多给 5 条结果，Agent 直接看结果就行。`
- 使用普通人可理解的词，可以保留专业技术词，但不得是黑话；必须保留的技术词，第一次出现时需要用一句朴实的人话清晰解释。
- 文风尽量幽默、轻松、可爱，但要平等、客观并基于事实，不能摆高姿态，不能高高在上教育人，不能拿费用、风险、隐私和用户知识水平开玩笑。

## 六条说人话规则

1. **先说事实，再下判断。** 写“需要安装 Python 和 6 个依赖包”，不写“具备一定的环境配置门槛”。
2. **主语必须清楚。** 判断与建议优先使用目标 Skill 的真实名称、`它`、`用户`或`你`。页首 Skill 定位第一句写出名称，第二、三句再次把 Skill 本身作主语时用“它”，第四句允许重新写出名称作收束。其他卡片或段落第一句写出名称后，后续再次把 Skill 本身作主语时用“它”。出现其他可能混淆的对象时，重新写出 Skill 名称。判断“是否重复指代 Skill”只看句子开头是不是拿 Skill 名称做主语，不是看名称有没有作为子串出现在句子任何位置——第三方服务、依赖的域名、模型名正常写出来，即使字面上恰好包含 Skill 名称（比如 anysearch 依赖 api.anysearch.com），只要不是把它当 Skill 自己的主语来用，就不算重复。指标句可以直接用指标名称作主语。“适合场景 / 不适合场景”和“这个 Skill 是啥”四张功能卡（使用方法、任务步骤、额外需要、最后交付）是短语列表，不套用主语规则，但不能出现“用户”这个主语，直接说能拿来做什么（`what.summary` 不受此限制，可以正常出现“用户”）。
3. **动作必须具体。** 写“用户要补三次资料”，不写“需要一定程度的人工参与”。
4. **能说结果，不说状态。** 写“项目文件没写清能否商用”，不写“使用许可未验证”。只有确实无法确认且无法进一步解释时才用“未验证”。
5. **一句只做一件事。** 连续出现两个以上逗号时，优先拆句。数字、条件和结论不要挤在一句话里。
6. **相信读者。** 同一事实只出现一次，不在段尾换一种说法再总结，不替读者制造误解后再纠正。

## 专业性从哪里来

- 用具体文件、数字、步骤、限制和来源支撑判断；
- 区分“官方说明”“根据规则判断”“安装实测”和“长期体验”；
- 不确定时指出缺什么证据，不用模糊话补洞；
- 轻松感来自清楚、自然和有节奏，不来自段子、夸张和网络口癖；
- 费用、权限、隐私、许可证和最终建议保持克制。

## 结论区固定写法

### Skill 定位

用 3—4 个短句：

1. `【Skill 名称】是【真实身份】。`
2. `它主要基于【能力基础】，通过【核心方式】完成【核心任务】。`
3. `最终用户可以得到【主要结果】。`
4. `经评估，【Skill 名称】更适合【典型用户】。`（适用对象不明显时再写）

页首 Skill 定位第一句必须以目标 Skill 名称开头。第二句要写清三件事——**基于什么能力基础、通过什么方式、完成什么任务**：句中要有“基于”二字说明能力基础（可以直接点出具体第三方服务、模型或工具名称，不用回避，即使这个名字碰巧和 Skill 名称有重叠字面，比如 anysearch 依赖 api.anysearch.com），再用“通过”二字带出具体方式，最后落到完成的任务上。例如：`它主要基于 api.anysearch.com 这一第三方联网搜索服务，通过通用搜索、垂直领域搜索、批量并行搜索和网页正文提取完成检索。` 第三句如果再次把目标 Skill 本身作主语，使用“它”；如果主语是用户或你，则直接写明。第四句可以重新写出目标 Skill 名称作收束。禁止用“这是一个”“这是一套”开头。

### 章节摘要

“这个 Skill 是啥”和“这个 Skill 好用吗”各保留一行摘要，保证章节完整：

- “这个 Skill 是啥”的摘要（`what.summary`）句式和内容跟页首定位第二句一致，但要更详细：写清这是一个用来干什么的 skill、主要依赖什么能力基础（可以点出具体服务名/模型名）、通过什么方式、完成什么任务、主要服务什么样的用户。不再单独设“能力基础”信息框，能力基础的具体内容直接写进这一行摘要里。示例：`anysearch 是一个给 AI agent 装上实时联网搜索能力的 skill，主要依赖 api.anysearch.com 这一第三方联网搜索服务，通过通用搜索、垂直领域搜索、批量并行搜索和网页正文提取完成检索任务，主要服务需要查AI技术资料、核实信息的用户。`（这一句允许出现“用户”，不受四张功能卡的无主语限制）
- “这个 Skill 好用吗”按“完整度 → 好用度 → 优势和不足哪个权重更大”的固定顺序概括；
- 摘要只报结论，四格和指标表再展开细节；
- 摘要可以与页首或结论概述重复核心判断，但不得复制完整句子或证据。

### 最终结论

固定 4 句，覆盖是否匹配需求、应用场景、能力基础、核心优势、不足这 5 个要点：

**第一句** 带目标 Skill 名称说明是否匹配需求，后面顺带一个小短句说清适合什么场景（跟“这个 Skill 适合你吗”那一节“适合场景”卡的内容可以重叠，两边都要写，不用互相避让）：

- `【Skill 名称】匹配你的需求，适合【一句话场景】。`
- `【Skill 名称】部分匹配你的需求，适合【一句话场景】。`
- `【Skill 名称】不匹配你的需求。`（不匹配时不用再补场景）

用户未提供具体需求时，按人群判断：

- `【Skill 名称】适合这类用户，适合【一句话场景】。`
- `【Skill 名称】部分适合这类用户，适合【一句话场景】。`
- `【Skill 名称】不适合这类用户。`

**第二句** 必须包含“能力基础”四个字，说清它靠什么、依赖谁完成任务，比如 `它的能力基础是 api.anysearch.com 这个第三方联网搜索服务。`

**第三句** 写核心优势，比如 `它的核心优势是有专门的学术和代码垂直搜索，比通用搜索更贴合技术研究。`

**第四句** 写不足或需要注意的地方，比如 `它的不足是官方文档会主动引导用真实邮箱自动注册账号。`

推荐条旁的判断对象由渲染器根据目标人群或具体需求、一般环境或当前设备自动生成，不在过程 JSON 中手写。

### 量化分析

固定两句，一句好用度、一句适合度，不是从七八个指标里随便挑：

1. 第一句先写好用度得分，再用大白话说清哪个维度拉分最明显。比如“好用度 7.6/10，核心免费、装起来简单，但要求自动注册账号这点拉低了风险表现。”
2. 第二句先写适合度得分，再用大白话说清跟需求贴不贴合、结果好不好用。比如“适合度 7.7/10，它的学术和代码搜索跟你的需求很贴合，结果能直接核对来源，但说不清数据具体从哪来。”

禁止出现“目标匹配”“交付匹配”这类内部指标名——用户看不懂这是什么意思，要翻译成"跟需求贴不贴合""结果好不好用/能不能直接用"这种人话。也不要为了显得专业自造"结构化结果""来源透明度"这类听着像术语但其实是临时编的词，想表达"来源透明度偏弱"就直接写"说不清数据从哪来"。

渲染器会把这两句里的“X.X/10”自动识别并标红，写作时按大白话正常写数字即可。这里的红色只变字色，不额外加粗、不放大字号（页面顶部“好用度：X.X/10”“适合度：X.X/10”那种大号加粗展示是另一处固定样式，跟这里无关，不用在 JSON 里操心）。

Skill 调用准确性是定性结果，放在指标表，不塞进量化分析卡。

结论概述不再单独设“适用场景”卡片——适合谁、用来做什么已经在最终结论第一句里带出，不重复展示。

### 使用建议

第一句必须写清动作，不带“它”这个宾语，也不加句号：

- 不推荐：`不建议安装`
- 谨慎采用：`建议先试用，再决定是否安装`
- 有条件推荐：`如果【具体条件】，可以安装`
- 推荐或强推荐：`建议安装`

禁止只写“有条件安装”“谨慎试用”这类标签句。条件必须说明需要什么 AI agent、软件、账号、材料或操作投入。

后续只说明什么时候可以考虑、先用什么材料或功能轻量试用、什么情况停用。

### 这个 Skill 适合你吗

顶部结论由渲染器根据分数重新生成，**不包含**最终结论第一句里那个附带的场景短句——场景内容只在结论概述的“最终结论”段落出现一次，这里不重复。不得另写第三套结论，JSON 里也不用为这句话单独填写内容。个性化需求模式和按目标人群判断模式的句式不一样，分别说明：

**个性化需求模式**：判断句用“你的需求”，因为需求是用户自己给的已经足够具体；判断句和使用建议是两句话，直接拼接，中间不加空格或标点：

- 不匹配：`【Skill 名称】不匹配你的需求。不建议安装`
- 部分匹配且需谨慎：`【Skill 名称】部分匹配你的需求。建议先试用，再决定是否安装`
- 部分匹配且有明确条件：`【Skill 名称】部分匹配你的需求。如果【具体条件】，可以安装`
- 匹配：`【Skill 名称】匹配你的需求。建议安装`

**按目标人群判断模式**：只有**一句话**，不再单独拼使用建议——直接用 `assessment_context.audience` 里写的具体人群，说清“适合谁安装”，不写“这类用户”这种空泛指代，也不在后面再补一句“建议安装”（那样会跟句尾的“安装”重复）：

- `【Skill 名称】不适合【audience】安装。`
- `【Skill 名称】部分适合【audience】安装。`
- `【Skill 名称】更适合【audience】安装。`

比如 `audience` 写的是“经常需要海选、筛选候选 Skill 的用户”，7.5 分以上时顶部结论就渲染成“【Skill 名称】更适合经常需要海选、筛选候选 Skill 的用户安装。”——一句话，句号前最后一个词是“安装”。这句由渲染器自动取 `audience` 字段拼接，不用在 JSON 里单独填写，也不用给这句话再加使用建议。

下方并列显示“适合场景”和“不适合场景”两张卡。每项直接写任务、偏好或使用条件，不写 Skill 名称、“它”“用户”，也不重复“适合”“不适合”。“适合场景”卡的内容跟最终结论第一句里的场景短句可以有部分重叠——两边分别服务不同的阅读场景（一句话速览 vs 完整列表），不用为了去重而牺牲任何一边的完整性。

### 四张功能卡

“使用方法、任务步骤、额外需要、最后交付”全部使用短句列表，2×2 排列：

- 每张卡写 2—6 条，每条只写一个对象或动作；
- 每条不超过 35 个汉字；
- 正文不出现“用户”这个主语，直接说能拿来做什么，比如写“想让 AI agent 查资料、核实信息时可以用”，不写“用户想让 AI agent 查资料”；
- 写“你要学习的书籍文件或本地文件夹”，不写“文件或路径”；
- 写“每课讲义与习题 / 知识摘要 / 学习路线状态”，不把多项交付挤进一句。

## 禁用表达

最终报告不得出现：

本文件是完整写作规则。渲染器只自动拦截其中部分高频表达，不能代替交付前人工质检。

- `不要把……理解成……`
- `并不是……而是……`
- `装上后，你最多……`
- `核心工作仍需其他能力完成`
- `可能会带来一定的……`
- `从某种程度上来说`
- `值得注意的是`
- `总体而言`
- `综上所述`
- `赋能`、`抓手`、`闭环`等没有新增信息的商业套话
- `具备一定的……能力`
- `需要一定程度的……`
- `在……方面表现良好`
- `可实现……`
- `核心路径通常不必`
- `联网必须，Key 可选`
- `按典型目标用户判断`
- `此分数不代表所有人`
- `接受静态、只读的采用评估`
- `目标用户需求`
- `采用代价`
- `证据边界`
- `这是一个`、`这是一套`
- 单独使用的`有条件安装。`
- 面向普通用户使用`仓库`，改写为“GitHub 项目”“项目文件”或“项目代码”
- `PDF 路径`、`Markdown 路径`、`核心路径`、`推荐路径`、`全开路径`
- `目标匹配`、`交付匹配`——这是内部指标名，用户看不懂，翻译成“跟需求贴不贴合”“结果好不好用/能不能直接用”
- `结构化结果`、`来源透明度`——这类听着像术语但其实是临时编的词，直接写人话，比如“说不清数据从哪来”

“路径”只用于真实的文件地址、网页地址或文件夹位置。表达不同用法时，直接写清条件和动作：写“学习 Markdown 文件时不用注册”，不写“Markdown 路径不用注册”；写“转换 PDF 时需要 MinerU”，不写“PDF 路径需要 MinerU”。

遇到不匹配，直接写“它不能完成什么”。遇到有条件推荐，直接列条件。

## 常见翻译

| 生硬表达 | 说人话 |
|---|---|
| 核心路径通常不必注册 | 通常不用注册账号 |
| 联网必须，Key 可选 | 必须联网；只有启用某项服务才需要 Key |
| 使用许可未验证 | 项目文件没写清能否商用 |
| 公开关注刚起步 | 目前只有 X Stars、Y 次提交，公开使用反馈不多 |
| 当前版本偏向 Claude Code | 说明按 Claude Code 写；换到其他 AI agent 需要改路径或命令 |
| 涉及的数据与隐私 | 哪些内容会发到外部服务 |
| 可能存在兼容性问题 | 尚未确认能否在 Windows 运行 |
| 典型目标用户 | 准备安装 Skill 的人；或直接写清具体人群 |
| 静态、只读评估 | 只看说明和公开资料，不安装、不运行 |
| 采用代价 | 要装什么、花多少钱、费多少 Token |
| 证据不足 | 目前没找到测试、价格或真实案例 |
| Markdown 路径可不使用 | 学习 Markdown 文件时不需要 |
| PDF 路径需要 MinerU | 转换 PDF 时需要 MinerU |
| 交付匹配 | 最后给你的东西是不是你要的 |

## 技术词翻译

优先使用以下表达：

| 避免直接写 | 改写为 |
|---|---|
| `multi_agent`、多 agent、子 agent | 多个 AI agent 协作 |
| LLM | AI 模型 |
| CI | 自动测试流程 |
| PR | 代码合并申请 |
| repo | GitHub 项目、项目文件或项目代码 |
| TDD | 先写测试，再写功能 |
| hook | 自动触发步骤 |
| runtime | 运行环境 |
| Python 数据库 | Python 依赖包；若确为数据库，写具体产品名 |

`CLI`、`API`、`MCP`、`Key` 首次出现时，用一句话说明它在本 Skill 中负责什么。禁止只堆缩写。

GitHub 项目没有明确许可证时，只能写“代码公开，暂未发现直接费用。项目文件没写清能否商用。”不得把“公开可下载”改写成“核心免费”。

## 长度限制

- 结论区每条不超过 55 个汉字；确有数字或产品名时可略超。
- 其他列表每条只表达一个判断，优先控制在 80 个汉字内。
- 结论区不用分号。出现两个以上逗号时，优先拆句。
- 一个卡片写 2—4 条，不写整段。

## 交付前删除测试

逐条检查：

1. 删掉后是否不影响判断？不影响就删。
2. 同一事实是否在两个位置出现？只留最合适的一处。
3. 能否把“侧面影响”改成“直接结论”？能就改。
4. 普通人第一次看到技术词是否知道它做什么？不知道就翻译。
5. 是否为了轻松而牺牲准确？是就收回玩笑。
6. 是否出现抽象判断，却没有具体对象、动作或结果？有就改成人、软件或服务实际做了什么。
7. 是否把同一事实分别写进结论、指标、卡点和适合区？只保留职责最匹配的一处。
